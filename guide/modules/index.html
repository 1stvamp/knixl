Using modules

A host file is mostly module nodes: openssh { ... }, user "wes" { ... }, zfs "8425e349" { ... }. Each node is handled by a module that knows which NixOS options to set for it. knixl ships with a set of modules built into the binary, so there’s nothing to install or copy before you use them.

For the exact fields any module accepts, run knixl doc <node> (or open Browse modules in the TUI). This page is the overview: what each module is for, and a short example to start from. Every example here generates as shown; the Examples section of the site has complete hosts with the Nix they produce.

Module For
os Core machine settings: boot loader, kernel, time zone, locale, sysctls, nix settings, system packages.
user A login user with groups and SSH keys.
openssh A hardened SSH server.
firewall Open ports, trusted interfaces, the nftables backend.
tailscale Tailscale, with its auth key from a secret.
package A package in environment.systemPackages.
zfs ZFS support and pools.
disko Declarative disk partitioning and formatting.
web-service An nginx reverse proxy with TLS.
security-headers One shared set of security headers for several nginx sites.
postgres A PostgreSQL server.
backups Scheduled restic backups.
incus An Incus container and VM host.
guest A NixOS container running on the host.
nix-ld Running prebuilt, dynamically linked binaries.
home-manager home-manager for one user.
import, raw-nix Escape hatches for Nix knixl doesn’t model.

The host node itself takes a few settings that aren’t modules: system (the platform, required), hostname (when it should differ from the host’s label), nixpkgs release= (see From KDL to a running machine) and oracle-modules (see Validation and the oracle). Add default=#true to one host (host "laptop" default=#true { ... }) and commands that need a host, like knixl install, use it when you don’t name one.

os

Section titled “os”

The settings every machine has. Each child is optional; set only what you want to differ from the NixOS default.

state-version sets system.stateVersion; leave it out when knixl.kdl has a system block, which sets it for every host. mutable-users #false makes NixOS the only source of users and passwords.

user

Section titled “user”

A normal login user.

hashed-password takes a hash from mkpasswd; there’s no way to give a plain password. On its own it only sets the initial password; add mutable-users #false under os if the declared one should always win.

openssh

Section titled “openssh”

An SSH server with password and keyboard-interactive logins switched off.

Without port, NixOS listens on 22.

firewall

Section titled “firewall”

The NixOS firewall. NixOS turns it on by default; this module opens what you need.

nftables #true switches the backend from iptables to nftables. Traffic on a trusted-interface bypasses the firewall entirely. enable, allow-ping and log-refused-connections take #true or #false and are only written when you set them. Ports opened here add to any opened by other modules, such as Tailscale’s open-firewall.

tailscale

Section titled “tailscale”

auth-key names a secret holding a Tailscale auth key, so the machine joins your tailnet on first boot (see Secrets, installers and images). Without it, you log in interactively. NixOS only passes up-flags to tailscale up when it logs in with the auth key; set-flags are applied with tailscale set every time the service starts, so settings that should always hold (like --operator) belong there.

package

Section titled “package”

Adds a package to environment.systemPackages. Usually you’d let knixl install write these lines for you; Packages and pins covers version pins and taking packages from other flakes.

zfs

Section titled “zfs”

The argument is the machine’s networking.hostId, which ZFS needs to import pools safely: eight hex digits, unique per machine (head -c4 /dev/urandom | od -A none -t x4 makes one). extra-pool imports a pool at boot, and arc-max-bytes caps the memory ZFS uses for its cache.

disko

Section titled “disko”

A declarative disk layout, which disko uses to partition and format disks (with nixos-anywhere, for example) and to set up the matching fileSystems.

A partition holds one of filesystem, swap, luks (which holds a filesystem of its own) or zfs pool="...", and zpool blocks declare the pools. On luks, password-file is read while formatting, and key-file is the key used to unlock at boot. disko’s own NixOS module has to be part of the system too. In a generated flake, declare disko as an input and list it in oracle-modules, which adds it to every host (see Other flake inputs); with your own flake, import disko.nixosModules.disko there.

web-service

Section titled “web-service”

An nginx virtual host proxying to an application, with TLS.

With acme, the certificate comes from Let’s Encrypt. hardened adds recommended security headers.

security-headers

Section titled “security-headers”

Applies one set of security headers to several nginx virtual hosts. knixl writes the header block once and refers to it from each site.

postgres

Section titled “postgres”

PostgreSQL with a hardened base configuration (local socket connections only, unless you add listen-tcp). database makes sure a database exists.

backups

Section titled “backups”

Scheduled restic backups. schedule is a systemd calendar expression. when is a Nix condition: the backup is only configured when it’s true, which suits a backup shared between hosts that don’t all run the service.

incus

Section titled “incus”

An Incus host: the daemon, the web UI, and the initial storage pool, network and profile. https-address-from-interface binds the API to an interface’s address when the machine boots, which suits an address handed out by Tailscale or DHCP.

guest

Section titled “guest”

A NixOS system container (containers.<name>) running on this host, configured with ordinary knixl modules.

Anything inside config is generated as the container’s own configuration. If you’d rather have an image to run under Incus, see guest-image in Secrets, installers and images.

nix-ld

Section titled “nix-ld”

Lets binaries built for other Linux distributions (a downloaded release binary, a rustup toolchain) run on NixOS, by providing the libraries they expect. List what they need; ldd on the binary tells you.

home-manager

Section titled “home-manager”

Manages one user’s home with home-manager’s NixOS module. state-version is required. Session variables only reach shells that home-manager manages. As with disko, home-manager’s own NixOS module has to be part of the system: in a generated flake, add it as an input and list it in oracle-modules; with your own flake, import it there.

import

Section titled “import”

Imports a NixOS module you wrote by hand. See When knixl doesn’t cover it.

raw-nix

Section titled “raw-nix”

Copies Nix into the generated module as written. See When knixl doesn’t cover it.

Settings shared by several hosts

Section titled “Settings shared by several hosts”

knixl has no include or inheritance between host files, so a block every machine needs (your user, SSH, nix settings) is either repeated in each host or, better, wrapped in a small module of your own: a base module whose emit sets the shared options, written once in modules/base/ and added to each host as base. See Writing your own modules.

Modules from elsewhere

Section titled “Modules from elsewhere”

You aren’t limited to these. A modules/ directory in your project holds modules you’ve written (see Writing your own modules), and knixl.kdl can declare modules published in other people’s flakes.

Some of knixl’s own modules are written the same way, as KDL files bundled with knixl: openssh, user, firewall, tailscale, zfs, web-service, security-headers and home-manager. A module of yours with the same node name replaces one of those (knixl tells you it’s doing so), which is how you’d change one to suit you. The others (os, disko, incus, guest, nix-ld, postgres, backups, package, raw-nix, import and host itself) are part of knixl’s code and can’t be replaced.
